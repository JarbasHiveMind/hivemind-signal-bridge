# AGENTS.md — `hivemind-signal-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a Signal messenger conversation to a HiveMind node: a HiveMind bridge
is a satellite whose input and output are a chat platform instead of a
microphone. Signal messages sent to a registered phone number become
`recognizer_loop:utterance` bus messages; the hub's `speak` replies are sent
back as Signal messages to the same sender. This bridge does not reimplement
the Signal protocol — it talks to a running `signal-cli` JSON-RPC daemon
(`hivemind_signal_bridge/rpc.py`, `SignalRPCClient`), which owns encryption
and the wire protocol to Signal's servers. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape:
[hivemind-telegram-bridge](https://github.com/JarbasHiveMind/hivemind-telegram-bridge)
and the other chat-platform bridges under the org — check them for prior art
before inventing a new pattern here.

## Layout / build / test

- Package module: `hivemind_signal_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks
  both `SignalRPCClient` and `HiveMessageBusClient`, so it runs without a
  live `signal-cli` daemon or hub — that also means it cannot catch a real
  handshake hang or a real JSON-RPC break; treat it as a shape/wiring check,
  not a live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindSignalBridge.__init__` builds (or
  accepts an injected) `HiveMessageBusClient` but does not connect it there —
  `HiveMessageBusClient.__init__` never opens a socket. The connection happens
  once, in `connect_hivemind()`, called from `start()`. Never add a second
  call to `connect()` or `run_forever()` — the client already owns and runs
  its own reconnect worker thread once `connect()` returns.
- **`connect()` must bound `handshake_max_retries`.** The `hivemind-bus-client`
  floor is `>=1.0.13a1`; that client's own default for `handshake_max_retries`
  is `None`, meaning retry forever. `connect_hivemind()` currently calls
  `self.client.connect(site_id=self.site_id)` without an explicit bound, so
  against a stalled or unreachable hub (down, wrong key/password) it hangs
  indefinitely instead of failing fast. This is a standing requirement, not a
  description of current behaviour: any change touching `connect_hivemind()`
  must add an explicit finite `handshake_max_retries`, exposed as a
  constructor parameter so operators can tune it, and rejected credentials
  must surface as a clean failure — not a bridge that spins forever looking
  connected.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`). This bridge
  has no way to grant itself permissions and must not try to work around a
  denial locally — a silently dropped message on the hub side is the hub
  doing its job, not a bug here. `allowed_senders`/`--allowed-sender` is a
  separate, bridge-side filter over which Signal numbers may originate
  traffic; it is not a substitute for hub-side message-type ACLs.
- **Return upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to Signal unmodified; do not reformat,
  truncate, or add bridge-specific decoration to hub-authored text. The one
  exception is the fixed fallback line on `hive.complete_intent_failure`,
  which is bridge-authored by design because the hub sent no utterance to
  relay.
- **Feedback-loop and pre-handshake guards stay in `_on_signal_notification`.**
  Messages from `signal_account` itself (the bridge's own sends echoed back
  by `signal-cli`) and messages arriving before `self._connected` is set must
  keep being dropped there, not forwarded and filtered downstream — forwarding
  before the handshake completes gets the connection killed by the hub.
- **`SignalRPCClient` is the only Signal-protocol surface.** All JSON-RPC
  framing, notification dispatch, and socket/TCP handling for `signal-cli`
  belongs in `hivemind_signal_bridge/rpc.py`; `HiveMindSignalBridge` only
  calls its public methods (`connect`, `close`, `send_text`) and its
  `on_notification` callback. Do not reach into `signal-cli`'s JSON-RPC
  payloads from `__init__.py`.
